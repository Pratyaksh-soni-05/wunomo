## 3. Known Gotchas

*This section only grows. Append; never delete. If a gotcha turns out to be fixed, mark it `[RESOLVED: <how/when>]` rather than removing it.*

- **A migration that defines a Postgres enum type with the Python enum's lowercase `.value` strings is wrong for every enum in this codebase — SQLAlchemy's default `Enum(PythonEnumClass)` stores the member's `.name` (uppercase), not `.value`, and `compare_metadata()` won't catch the mismatch.** Found writing item 6's `509a9b8715f2` migration: it listed `'draft_plan'`, `'plan_rejected'`, etc. (the lowercase values every enum in this codebase's Python classes actually holds — e.g. `TaskStatus.DRAFT_PLAN = "draft_plan"`), but a direct `pg_enum` query against the real dev DB confirmed every existing enum type (`personalitymode`, `runstatus`, `pipelinestatus`, etc.) stores the uppercase member **name** instead (`SUCCESS`, not `success`) — confirmed further by a real row: `pipeline_runs.status` literally contains `'SUCCESS'`. This is SQLAlchemy's documented default behavior for `Column(SAEnum(SomeEnumClass))` with no `values_callable` override, and every existing migration in this repo that defines one of these enum types already gets it right (`sa.Enum('PENDING', 'RUNNING', 'SUCCESS', ...)`, always uppercase — checked `7e3773979374` directly). **The existing schema-drift test (`test_schema_drift.py`'s `compare_metadata()` check) did not catch this** — it diffs table/column/index/FK existence, not enum label content, a real blind spot confirmed by deliberately reintroducing the bug and watching `compare_metadata()` stay green. Closed with a new, targeted test (`test_migrated_task_enum_labels_match_the_python_enum_member_names`) that queries `pg_enum` directly against a scratch DB and compares to each enum class's real `{member.name for member in EnumClass}` — proven to actually go red first (per the drift-detection test's own "a test that can't fail is worse than none" standard), currently scoped to the 4 new Task enums but the same pattern generalizes to any enum this codebase adds next. **When writing a migration for any new `SAEnum`-backed column, use the Python member names (uppercase), never the values — and don't trust `compare_metadata()` alone to catch it if you get this wrong.**

- **Two docker-compose.yml files, not one.** `dataops-agent/docker-compose.yml` (root, referenced by the README quick-start) and `dataops-agent/backend/docker-compose.yml` both stand up the full stack independently, with different container/network names and different Postgres/Redis healthcheck behavior. Running both simultaneously will port-collide on 8000/5432/6379. Always confirm which one a command/doc is referring to before running `docker compose` commands.
- **The frontend service is commented out in the root compose file.** `docker compose up` never starts a frontend even after the missing files are restored — you must uncomment it in `dataops-agent/docker-compose.yml` first.
- **`.gitignore` in this repo only covers Python.** `[RESOLVED: initial commit]` — a Node/Next.js block (`node_modules/`, `.next/`, `out/`, `.vercel`, `.turbo/`, etc.) was added before the first commit, and the ~11.5k already-staged `node_modules`/`.next` files were unstaged. Still double-check `git status` after any broad `git add -A`/`git add .` inside `dataops-agent/frontend/` in case new build output reappears.
- **JWT tenant_id is trusted, never re-validated against the DB — and this applies to every claim in the token, not just tenant_id, including `role`.** `get_current_user()` (`api/v1/auth.py`) is a bare `jwt.decode()` with no DB lookup at all — no `is_active` check, no fresh `role` read, nothing. If you ever add a "deactivate tenant," "remove user from tenant," or "change a user's role" feature, remember that a previously-issued JWT for that user stays valid, **with its original claims**, until it naturally expires — there's no revocation and no per-request re-check. Concretely: `PATCH /team/members/{id}/role` updates the DB row, but the affected user's *existing* session keeps operating under their *old* role (both for `require_role()` gates and for whatever the frontend decodes client-side via `decodeUserFromToken()`) until they get a fresh token — either by naturally re-logging-in, or by the token expiring and them being forced to. Same for `DELETE /team/members/{id}`'s soft-removal (`is_active = False`): the removed member's still-valid JWT continues to be accepted by every authed endpoint, unchanged, until expiry — **confirmed live during Phase 17's Team build** (a JWT captured immediately before removal was replayed against `GET /team/members` afterward and returned a real `200`). The only path that's actually real-time is a *fresh* login attempt, since `resolve_password_login()` filters `is_active` at that specific moment (see the separate, already-documented Gotcha that this still isn't true for Google/email-code login). **When building any UI around role/removal, don't imply the effect is immediate for an already-open session** — it's immediate for the DB and for anyone who logs in fresh afterward, not for a session already in flight. **This is now tracked as a real fix item, not just documented behavior — see the new "Removed/demoted members keep access for up to the JWT TTL" Known-broken row below** (severity, exact TTL, and fix directions).
- **Tenant scoping is a per-query convention, not a framework guarantee.** Every new query against a tenant-owned table must manually add `.where(Model.tenant_id == tenant_id)`. There is no base repository/query class to inherit this from. When reviewing or writing any new DB query in this codebase, explicitly check for the tenant filter — it is the single easiest way to introduce a cross-tenant data leak here.
- **Two different LLM fallback mechanisms coexist.** `services/llm_service.py` has both `get_llm_for_agent()` (LangChain `.with_fallbacks()`, used by the actual agent graph) and `invoke_llm()` (manual tenacity-retry + manual fallback, apparently unused by the graph). Don't assume changing one changes the other's behavior.
- **Ingestion connectors expose a raw `execute_sql()` that bypasses `SqlRunner`'s safety layer.** `SqlRunner` (the safe, keyword-blocked, parameterized path) is one specific caller; `postgres_connector.py` and `mysql_connector.py` both independently expose `execute_sql()` methods that run arbitrary SQL with no keyword filtering. If you add a new caller, go through `SqlRunner`, not the connector directly, unless you've deliberately re-derived the same protections.
- **`python_runner.py`'s in-process `exec()` sandbox is intentionally not airtight.** It AST-allowlists imports/names and uses a restricted builtins namespace + thread timeout, but the code's own docstring says this is "sufficient" only for already-LLM-validated code, not untrusted input, and recommends a real microVM (gVisor/Firecracker) for anything stronger. Don't expose this path to raw user-submitted Python without adding real process isolation first.
- **Debug/patch scripts in `backend/` root are leftover hotfixes, not part of the app.** `diagnose.py`, `fix_analytics.py`, `fix_analytics2.py`, `patch_analytics.py` were run manually inside the container (they hardcode the `/app/...` container path) to patch a `NoneType has no attribute 'value'` crash in `/api/v1/analytics/pipelines` caused by NULL pipeline-status rows in a groupby. The underlying fix should already be reflected in `api/v1/analytics.py` itself — if you're debugging analytics and considering writing a new one-off patch script, first check whether `analytics.py` already has the fix these scripts describe, and prefer fixing it in place over adding another patch script to the pile.
- **Test suite hits whatever DB `APP_ENV=test` resolves to — there's no isolated test DB or per-test reset — and the same is now true of Redis for anything rate-limited.** `conftest.py` builds an `AsyncClient` against the real `main.app` with no fixture-level DB setup/teardown. Running tests repeatedly can accumulate rows; use a unique/random email per test (most tests already do — `test_register_and_login` didn't, and a hardcoded email accumulating duplicate tenants across repeated runs is exactly what made login()'s disambiguation fix start (correctly) failing that test — fixed by giving it a unique email like everything else). The email-code auth system's Redis-backed rate limiters (`services/auth_service.py`) have the identical problem in a new form: the per-IP counter (`otp:ip:{ip}`) is shared across every test run in a session, real curl testing, and the pytest ASGI test client alike, since none of them get a distinct IP and Redis state isn't reset between invocations. Heavy manual live-testing against `/auth/email-code/request` right before running `pytest` can leave the per-IP counter primed near/over its cap, causing an unrelated later test run to fail with `rate_limited` for reasons that have nothing to do with that run's own test logic. If an email-code test fails this way, check `redis-cli KEYS "otp:*"` before assuming the code is broken — `redis-cli --scan --pattern "otp:*" | xargs redis-cli DEL` clears it (safe, it's all short-TTL test/dev state). Don't assume test runs are hermetic, for either store.
- **`RISK_ACTIONS["high"]` names tools that don't exist** (`delete_records`, `drop_table`, `modify_schema`, `revoke_access`). If you're asked to "make destructive actions require approval," check whether the actual mutating tool (e.g. `execute_sql_transform`, `resolve_incident`) is even in that risk table before assuming the gate already covers it — right now, most real mutating tools default to whatever risk tier `get_risk_level()` falls back to, not `"high"`.
- **Approvals created mid-chat (via the LangGraph `approval_gate_node`) do not show up in the `/api/v1/approvals` queue.** Only approvals created through `PolicyEngine.create_request()` (e.g. via `seed_approval.py` or a correctly-written tool) persist to the DB. If a user reports "the agent said it needs approval but I don't see it in the approvals list," this is why — check whether the code path that created it actually called `create_request()`.
- **Celery beat's scheduled pipeline-run task call looks arg-mismatched** — **[RESOLVED: Phase 19, P0 item 5]** — was a symptom of a bigger, now-fixed issue (the whole dynamic per-pipeline scheduling design was unreachable, not just arg-mismatched). Replaced with a real, live, static-polling mechanism (`check_scheduled_pipelines()`), live-verified against a real `* * * * *` schedule. See the Status Table row.
- **Mutating `celery_app.conf.beat_schedule` from the `backend` (FastAPI) process has zero effect on the `celery_beat` process's actual running schedule — they don't share memory, and Celery's default `PersistentScheduler` isn't a shared/cross-process store.** Found while fixing the scheduled-pipelines cluster: `modules/orchestration/scheduler.py`'s `Scheduler.register()`/`sync_all()` were designed to inject dynamic per-pipeline entries into exactly this dict at runtime, from whichever process calls them — but a call from an API request handler (running in `backend`) can only ever mutate `backend`'s own private copy, never the separate `celery_beat` container's in-memory schedule. **If a future feature needs truly dynamic (not just DB-polled) per-item Celery beat scheduling, it needs a genuinely shared store — RedBeat (Redis-backed) or `django-celery-beat` (DB-backed) — not a bare mutation of `conf.beat_schedule` from a different process than the one running beat.** The pattern that *does* work across this process boundary, used for the actual fix: a static beat entry (defined once in `celery_app.py`, present in every process from boot) that polls the database directly on each tick — exactly how `check_all_freshness()` and the new `check_scheduled_pipelines()` both work.
- **`celery_worker`/`celery_beat` don't hot-reload code changes, same as `backend` (see the existing `docker compose restart backend` Gotcha) — restart both explicitly after editing anything in `services/tasks.py`, `services/celery_app.py`, or any module they import.** Cost real time while verifying the scheduled-pipelines fix: both containers had been running for hours before the new task/beat-entry code was written, and `docker compose restart celery_beat celery_worker` was required before the new `check-scheduled-pipelines-1min` entry or `check_scheduled_pipelines()` task were even registered — a live poll against the running server showed nothing happening until both were restarted.
- **A `RuntimeError: ... got Future ... attached to a different loop` / `Exception closing connection <AdaptedConnection ...>` warning in Celery worker logs around some task boundaries is a pre-existing, already-present quirk of this codebase's `asyncio.run()`-per-task + pooled-asyncpg-connections pattern — confirmed benign, not a new regression, before assuming otherwise.** Found while live-verifying the scheduled-pipelines fix: both the new `check_scheduled_pipelines()`/`execute_scheduled_pipeline_run()` tasks *and* the untouched, pre-existing `execute_pipeline_run()` task show the identical error signature in the logs (confirmed by grepping worker logs for both task names) — so it predates this session's changes and isn't something the new code introduced. Every task observed still completed successfully with correct DB state (`Task ... succeeded`, and the real `PipelineRun` rows this warning surrounds were confirmed correct via a live API poll) despite the warning appearing. Root cause is the same class of issue `engine.dispose()` (called at the top of every task, already present before this session) exists to mitigate — a stale asyncpg connection object from a previous `asyncio.run()` call's now-closed event loop getting garbage-collected during a *later* call's loop, which logs a cleanup error but doesn't propagate a real failure. **Not fixed — out of scope for this session** since it predates the changes made here and doesn't affect correctness; flagging so a future session doesn't mistake this cosmetic noise for a new bug when touching Celery task code.
- **`RunTracker` is a pass-through, not a separate system.** It exists only "for agent tool compatibility" (per its own comment) and just delegates to `DAGManager`. Don't look for run-tracking logic there — it's in `dag_manager.py`.
- **There is no real DAG.** Despite the name `DAGManager` and the module path `modules/orchestration/`, pipeline execution is a fixed linear sequence (sync → quality check → done), not a graph with dependency resolution. If a task asks you to add a new pipeline step, you're inserting into a linear chain in `tasks.py`'s `_execute_run`, not registering a DAG node.
- **Any LangGraph node you add to `agent/dataops_agent.py`'s `StateGraph` must return only the new/delta value for reducer-annotated channels, never the full accumulated state.** `AgentState.messages` uses `Annotated[Sequence[BaseMessage], operator.add]`, so LangGraph automatically appends whatever a node returns onto the existing value. Returning `state["messages"] + [new]` (instead of just `[new]`) — which every custom node in this file did until the fix — makes the reducer concatenate old+new onto the already-accumulated state, doubling history on every node hop (a 3-message conversation reached 63 messages in 3 turns). `ToolNode` (the one prebuilt node here) has always done this correctly; match its pattern for any new custom node.
- **Any new tool exposed to the agent must never accept `tenant_id` (or `user_id`/`session_id`) as an LLM-suppliable argument that isn't also force-corrected server-side.** Tool schemas require these as function-call arguments the LLM itself generates, but the LLM has no reliable way to know the real value — it will hallucinate a placeholder unless told, and can still get it wrong even when told. `agent_node` in `dataops_agent.py` now force-overwrites `tenant_id` on every outgoing tool call to the real, server-derived value; if you add a tool that takes `tenant_id` (or add `user_id`/`session_id` as tool args for the first time), extend that same override loop rather than trusting the LLM's argument. All tools in `ALL_TOOLS` now take `tenant_id` this way — `get_cicd_status` was the last holdout and is fixed (see Status Table).
- **`FALLBACK_LLM_MODEL` must be a model capable of reliable tool-calling.** `llama-3.1-8b-instant` on Groq fails real tool-calling requests outright with a `tool_use_failed` 400 error (malformed function-call generation) — it only ever looked "fine" in testing that didn't exercise tool calls. Keep this set to `llama-3.3-70b-versatile` (or an equally capable model) — `config.py`'s own default already documents this; don't let `.env` drift back to a cheaper/faster model without re-testing an actual tool-invoking chat message live.
- **No agent tool should ever call back into this app's own REST API over HTTP.** Tools should call the same service-layer functions the REST endpoints call, in-process — that's the pattern every tool follows (`modules/*` classes, or plain functions in `services/*.py` like `cicd_service.py`). An HTTP round-trip back into your own API (`get_cicd_status` did this until fixed — see Archive) is a sign a tool was stubbed out before the shared service layer existed, and it silently loses auth/tenant context in the process: `httpx` doesn't raise on a 4xx by default, so a failed/unauthenticated self-call can return empty defaults (`{}`, `0`, `"unknown"`) instead of an error. Treat any tool whose failure mode is unusually generic zero/empty defaults as a signal to check whether it's swallowing a failed call this way.
- **"Verified live" only proves the exact code path that specific test exercised — write regression tests against the real model/schema, not assumptions about column names.** `get_pipeline_for_repo()` referenced `Pipeline.is_active`/`Pipeline.source_config`, neither of which exist (real columns: `status`, `pipeline_config`) — it would have raised `AttributeError` on its very first real call, forever, since the function was written. There was no mock or fixture to blame (no automated test existed for it at all); the original fix was verified manually/live, and that manual pass most likely exercised a different code path (setting `pipeline_config` at pipeline-creation time, which has always used the correct field name) than the one that was actually broken (the function itself, plus the update path). When you add a regression test for a DB-touching fix, prefer hitting the real model via a real session (see `test_cicd_service.py`, `test_pipeline_run_status.py`) over a hand-rolled mock — a mock can only be wrong about the schema in the same way the code under test is already wrong, silently agreeing with itself.
- **The primary→fallback LLM handoff has a hard 15-second ceiling (`PRIMARY_LLM_TIMEOUT_SECONDS` in `services/llm_service.py`) — don't remove it or "simplify" back to bare `.with_fallbacks()`.** A failing Gemini call doesn't fail fast on its own: google-api-core's gRPC retry layer honors the server's suggested `retry_delay` (observed 40s+), and `langchain_google_genai`'s own hardcoded tenacity retry (`max_retries=2`, backoff up to 60s) sits on top of that — neither is configurable from outside, and `ChatGoogleGenerativeAI`'s `timeout` constructor field is dead code in the installed version (never wired to the actual request — verified by grepping the library source for `self.timeout`, zero hits). Measured live: 2m22s before this fix, 14.7s after. If you're tempted to raise/remove the 15s ceiling because "it might cut off a slow-but-working Gemini call," Groq's own responses have consistently landed in the 2-12s range in testing, so 15s already has margin — don't just trust a config field on the primary model to bound this instead, confirm it actually works with a live forced-failure test first (it didn't, here).
- **`get_agent()`'s module-level `_cache` dict in `agent/dataops_agent.py` is keyed only by `"{personality}:{operation}"` — this will break once per-tenant AI model selection ships (`FRONTEND_BUILD_PLAN.md` Phase 16).** — **[RESOLVED: Phase 16]** The cached value is a fully-built agent object with a specific primary/fallback LLM already bound in. If tenants can choose their own model, the SAME cache key today would serve tenant A's cached agent (built with tenant A's model choice) to tenant B on a matching personality/operation combo — silently leaking one tenant's model preference into another tenant's requests. **Fixed exactly as planned here**: `get_agent()` now requires `tenant_id` (raises `ValueError` if omitted — can't silently regress back to the old key by a caller forgetting to pass it) and the cache key is `f"{tenant_id}:{personality}:{operation}:{primary_model or 'default'}"`. `run_agent()` resolves the tenant's real, DB-stored, allowlist-validated model override (`services/settings_service.get_ai_model_override()`) before calling `get_agent()`. **Live-verified exactly per this Gotcha's own instruction**: two real tenants, one with `ai_model_override: "llama-3.3-70b-versatile"` and one with no override, made real back-to-back chat requests — `llm_usage_events` confirmed tenant A got `provider: "groq", model: "llama-3.3-70b-versatile", used_fallback: false` (a genuine primary call on its own override, not an accidental fallback) and tenant B got `provider: "gemini", model: "gemini-3.5-flash"` — no cross-tenant leak. See the "get_agent() cache re-keying + AI model override" Status Table row for full detail.
- **All Python enums in `models/all_models.py` use UPPERCASE member names with lowercase string values** (e.g. `RunStatus.SUCCESS = "success"`, `PipelineStatus.ACTIVE = "active"`, `IncidentStatus.OPEN = "open"`) — the opposite convention from `models/cicd.py`'s enums (`CICDStatus`, `GateDecision`, `DeploymentStatus`, and cicd.py's own separate, unused `IncidentStatus`/`IncidentSeverity`), which use lowercase members. This mismatch was independently miswritten as lowercase-member access (`RunStatus.success`, `PipelineStatus.active`, `IncidentStatus.open/investigating/resolved`) in **6 different files** — `incident_manager.py`, `monitor.py`, `anomaly_detector.py`, `scheduler.py`, `business_rules.py`, `report_generator.py` — all fixed and live-verified this session (see Status Table), but the fact that it recurred independently 6 times strongly suggests it's an easy mistake to make here specifically (lowercase values, easy to assume lowercase members too). **When writing or reviewing any new comparison against `RunStatus`/`PipelineStatus`/`IncidentStatus`/`IncidentSeverity` from `all_models.py`, double check the member name is uppercase** — and if you're touching `models/cicd.py`'s enums instead, remember those really are lowercase, so don't "fix" them to uppercase by pattern-matching this gotcha.
- **A Status Table "How verified" cell that only restates what the code claims to do, instead of citing a specific live call or regression test, means it probably wasn't actually verified.** The entire enum-case bug cluster above hid behind exactly this pattern — Observability's and Reporting's rows both read like proof ("real DB-aggregate freshness/health metrics", "real LLM-powered incident triage", "read in full, no stubs") but named no live test, because there wasn't one; every code path they described raised `AttributeError` on its very first real call, silently swallowed into `{"error": ...}`. Phase 4's customer-simulation pass gave real, live, end-to-end coverage to the CI/CD incident system (webhook → risk-check → approval → deploy) but never touched the general DataOps `Incident`/`Monitor`/`AnomalyDetector`/`ReportGenerator` code paths — two different "incident" systems exist in this codebase (`models.all_models.Incident` vs `models.cicd.CICDIncident`), and only one got exercised. When reading this Status Table (or writing a new row into it), treat "How verified" text that doesn't name a specific test file, live request, or reproducible command as a claim to re-check, not a fact to build on.
- **`agent/tools/*.py` was written against an imagined API surface for `modules/*` that was never cross-checked against the real implementation — treat any tool you haven't personally live-verified as unverified, regardless of what the Status Table says elsewhere.** Evidence this is one process-level root cause, not scattered noise: the wrong class name `RuleEngine` (real: `QualityRuleEngine`) was independently guessed the same way in two unrelated files (`business_rules.py` and `quality_tools.py`); the wrong method names across the board are consistently plausible-sounding-but-never-real (`.query()`, `.detect()`, `.send()`, `.standardize()`, `.status_report()`) — the signature of code written from a tool's docstring/intent rather than from reading the target class. It manifests in at least 4 distinct mechanical shapes with no single fix: wrong class name, wrong method name, wrong enum-member case (the cluster fixed this session), and return-shape mismatches (e.g. `business_rules.py`'s `list_rules()` bug) — plus at least one outright missing feature (`LineageTracker` has no contract methods despite `governance_tools.py` calling `.create_contract()`/`.validate_contract()`). See the new Known-broken row ("22 more `agent/tools/*.py` call sites...") for the full punch list; two static sweeps (module-import check, call-site-existence check) are exhaustive for the wrong-name flavors, so that list doesn't need re-discovering — but isn't exhaustive for return-shape or missing-feature bugs, which need per-site review or live testing to catch.
- **This dev DB's schema was never actually created by Alembic — `alembic_version` doesn't even exist.** `main.py` calls `Base.metadata.create_all()` on backend startup (line ~28), and that's what has been creating every table this whole project, migrations included — Alembic's own migration chain (`7e3773979374` → `db3efa7d4d82` → `fe6e4b941fce`) has never actually been applied to this database. Running `alembic upgrade head` from this state fails immediately (`DuplicateObject: type "approvalstatus" already exists`) because it tries to replay the full migration history against objects `create_all()` already created. **Don't run `alembic upgrade head` against this dev DB without first checking `SELECT * FROM alembic_version` — if that table doesn't exist, the fix for a brand-new table is to restart the backend container (triggers `create_all()`, which only creates missing tables/indexes — no migration run needed).** This also explains and generalizes the already-documented "Missing migrations for 2 of 3 CI/CD tables" Known-broken entry — it's not that 2 tables specifically are missing migrations, it's that Alembic isn't the real source of truth for schema in this environment at all. Still write the migration file for every new model (it's correct, reviewable, and will matter for a real production deploy where `create_all()` presumably isn't what runs) — just don't expect `alembic upgrade head` to be how it actually lands here. **For a migration that alters an *existing* table (new column, nullable change, etc.), `create_all()` can't help — it only creates missing tables, never alters ones that already exist.** Phase 5's `User` migration (nullable `hashed_password`, new `google_id`/`email_verified`) needed this for real, and the fix is straightforward: verify the DB's actual current schema matches the migration chain's expected state at the previous head (spot-check a table or two), then `alembic stamp <previous_head_revision>` (marks that revision current without running anything — safe, since `create_all()` already produced an equivalent schema) followed by a normal `alembic upgrade head`, which now only has to apply the one genuinely new migration. Worked cleanly here; this is the real, durable fix for the underlying drift, not a one-off workaround — repeat it for any future migration that alters existing tables rather than just adding new ones. **Update, Phase 19 migration-drift session (2026-08-02) — the migration *files* are now verified to build a correct, complete schema from empty; this dev DB's own state is unchanged and still not what this paragraph describes fixing.** `alembic upgrade head` now runs cleanly start-to-finish against a genuinely empty database — verified on an isolated scratch Postgres 16 container, never this dev DB, which was not touched, restarted, or migrated by that session. Two real gaps were found and fixed in the migration files themselves: `pipeline_commits`/`pipeline_deployments` had no migration creating them at all (new `609092d6978f_add_cicd_pipeline_tables.py`), and `team_invites` was missing its `ix_team_invites_created_at` index (fixed in `a4f7c92b1d05`) — see both now-resolved Known-broken rows and the new "Migration-drift verification" Status Table row for the full methodology and proof (an `information_schema` diff against a `create_all()`-built baseline, byte-identical across all 24 tables). **The significant finding, stated plainly: neither of this project's two schema-creation mechanisms — not Alembic, not `create_all()` — could bootstrap a genuinely empty database, for the same root cause.** Both assumed the 3 CI/CD enum types (`cicdstatus`/`gatedecision`/`deploymentstatus`, `models/cicd.py`, all declared `create_type=False`) already existed rather than creating them. `create_all()` never creates a `create_type=False` type itself (that's what the flag means); the pre-existing Alembic chain never created them either (see the now-resolved "Missing migrations for 2 of 3 CI/CD tables" Known-broken row). Confirmed live: running the exact `create_all()` call `main.py`'s lifespan hook makes, against a genuinely empty scratch DB, failed with `UndefinedObjectError: type "cicdstatus" does not exist` until those 3 types were created by hand first — the identical failure class as the fresh `alembic upgrade head` run. No `create_enums.sql` or equivalent exists anywhere in this repo, in any commit, ever. **The practical consequence: this project was effectively unbuildable from a truly empty database by any means this repo could reproduce, and nothing before this session would have told you that** — the real dev DB has been running this whole time only because someone, at some unrecorded point, ran 3 `CREATE TYPE` statements by hand and never wrote them down anywhere; every fresh clone, new environment, or disaster-recovery restore was one `docker volume rm` away from being unable to start the app at all, silently, until whoever hit it spent real time debugging an `UndefinedObjectError` with no lead as to why a supposedly-working `create_all()` call would ever produce one. Fixed now (the new migration creates these 3 types for real, via plain `sa.Enum(...)` which does self-create) — but the underlying lesson generalizes: a `create_type=False` declaration is a claim that something else guarantees the type exists, and this repo had nothing that did. **This dev DB itself still has no `alembic_version` table and is still exactly as this paragraph originally described** — reconciling it (via `alembic stamp` at the right revision, following this same paragraph's own worked example for the `User` migration) is a separate, not-yet-done action; this session only verified and fixed the migration *files*, per explicit instruction not to touch the dev DB.

Hard Rule 4 is enforced explicitly, not left to the driver's own error message: a literal `host == "localhost"` is caught and named *before* any connection attempt, since inside Docker that resolves to a real, listening loopback — the connection doesn't fail with a DNS error, it gets a confusing `ConnectionRefusedError` a user could easily misdiagnose as "the database isn't running" rather than "you typed the wrong host" (confirmed empirically, not assumed, by attempting a real `asyncpg` connect to `localhost` from inside the backend container). Failure reasons are real, driver-sourced messages mapped to specific categories (`auth_rejected`, `database_not_found`, `connection_failed`, `timeout`, `missing_field`), each verified empirically against the real dev Postgres container rather than guessed from documentation — e.g. wrong password raises `asyncpg.exceptions.InvalidPasswordError`, an unknown database raises `asyncpg.exceptions.InvalidCatalogNameError`, and MySQL's `pymysql.err.OperationalError` carries a numeric code (1045 auth, 1049 unknown database, 2003 everything connection-level) inspected via `e.args[0]` rather than string-matching the message. CSV/Excel (upload-flow, already validate via a real file read) and API_REST/Google Sheets (no per-field form yet, still the raw JSON textarea) are out of scope for this pass — the frontend "Add Source" modal shows an explicit "Not test-checked before saving today" note for those types rather than implying they were checked.

- **`register_source()` (`modules/ingestion/connector_manager.py`) reports a refusal as a plain `{"error": "..."}` body on an HTTP 200, never an HTTP error status — `POST /api/v1/sources/`'s route handler just returns whatever dict it gets back, so a 200 alone never meant "created."** Found live 2026-09-04 while verifying slice 5's Test Connection feature: tested a real connection against `postgres`/`dataops` (this stack's own control-plane database, the only real Postgres readily available in dev) and it correctly succeeded — but the frontend's `createMut` (`sources/page.tsx`) unconditionally showed "Source created," closed the modal, and invalidated the list on ANY 200 response, with no row ever actually persisted (`_points_at_app_database`'s guard silently refused it server-side). - **Sidebar split (Wunomo Projects Phase 2 frontend, slice 6, 2026-09-05) — the frontend's first consumption of channels at all.** The full channel backend (create/list/get, user+agent membership, `@mention` routing, per-agent context filtering) shipped 2026-09-03 and sat completely unused by the frontend until this change — `api.ts` had zero `Channel` code, `SessionList.tsx` rendered one flat list. Now split into "AXIOM Direct" (unchanged private sessions) and "Channels" (new). A channel with zero agent members is a guaranteed dead end (`resolve_mentioned_agent`/`channel_agent_members` both refuse to route into one), so channel creation requires picking at least one agent in the same flow — no bare name-only create.

  **Three distinct mention-resolution failures, not one generic message (explicit user requirement, since slice 8 hasn't built `@mention` autocomplete yet — every mention is still hand-typed)**: `services/channel_routing.py`'s new `find_active_agent_in_tenant()` disambiguates what `resolve_mentioned_agent()`'s bare `None` can't by itself. `@Name` matching no ACTIVE agent anywhere in the tenant → "doesn't match any agent in your workspace" (a typo — needs a spelling fix). A real, active agent that exists but isn't a member of *this* channel → "X exists but isn't a member of this channel yet. Add them from this channel's members..." (a membership gap — needs an add-member action, which is why slice 6 also had to ship a minimal "+ Add Agent" control on the channel view itself, not just at creation time, or this message would point at a UI that doesn't exist). An offboarded agent's name reads as the *first* case ("doesn't match"), not the second — from the mentioning user's perspective it's the same dead end as a typo, since there's no reactivation endpoint and claiming "isn't a member yet" would incorrectly imply adding them back would work. The pre-existing two no-mention cases (zero agents vs. multiple, `chat.py`) were left as-is except the zero-agents message, which now names the actual fix ("add one from this channel's members") instead of the old "please @mention" — misleading with nobody left to mention.

  **Offboarding meets channels — deliberately not blocked.** What the code did before this change: `offboard_agent` (slice 4) already deleted an agent's `channel_agents` rows regardless of whether it was a channel's only member, and the old no-mention "No agents are in this channel" message told the user to "please @mention" with no one left to mention — a silent, self-inflicted dead end. Fixed without blocking offboarding: blocking would mean enumerating every channel an agent is the sole member of and refusing until each is fixed, which risks making offboarding a heavily-used agent effectively impossible, and breaks the precedent this build already set (`agent_sources`, channel history, project membership all survive offboarding, never gate it). Instead, `GET /api/v1/channels/` now returns `agent_count` per channel (0 means unusable right now, whether it never had an agent or lost its only one to offboarding) so the sidebar shows a "needs an agent" badge *without the user having to open the channel first* — confirmed live: offboarding a channel's sole agent dropped its `agent_count` from 1 to 0 and the badge appeared in the sidebar immediately. `offboard_agent` also logs `channel_left_without_agent` (channel_id, offboarded agent id/name) purely for operator visibility, never as a gate.

  **A routing failure renders distinctly from a real reply, not as if an agent said it.** `_no_route_response()` (`chat.py`) is the only place `provider` comes back `null`; `LocalChatMessage.isSystemNotice` is computed from exactly that at send time and styled without an avatar, muted and italic. Not reconstructable from `GET .../history` (no per-message `provider` field persisted) — an acceptable, cosmetic-only gap on reload, since the message text itself is self-explanatory.

  **Confirmed, not assumed: `GET /api/v1/channels/` was already scoped to the caller's own membership**, not every channel in the tenant (`join(ChannelUser, ...).where(..., ChannelUser.user_id == user["sub"])`) — no fix needed, just verified before building on top of it.

  **Observed while cleaning up live-verification data, worth knowing**: a routing failure (`_no_route_response`) returns before either `ChatMessage` INSERT in `chat.py` (lines ~285/304) ever runs — a hand-typed typo or an unmentioned-member attempt is never persisted to history at all, only a message that actually reached an agent is. A channel's visible message count in the UI can therefore be lower than the number of messages a user visibly sent, if some were routing failures. Not a bug — there's no real state to preserve from a message nobody answered — but worth knowing before assuming message count reflects every send attempt.

- **Channel membership management shipped 2026-09-05 (Wunomo Projects Phase 2 frontend, slice 7) — completes what slice 6 deliberately deferred.** The backend already had full CRUD for both human (`ChannelUser`) and agent (`ChannelAgent`) membership since 2026-09-03; the frontend consumed none of it until now beyond slice 6's own "+ Add Agent." `MessageThread.tsx`'s old single-purpose modal is now one "Members" modal: current agents/people each with a remove control, addable agents/people (the latter sourced from the existing `GET /api/v1/team/members`/`getTeamMembers()` — no new tenant-user-listing endpoint needed) each with an add control.

  **Removing the last human member is blocked (explicit user decision), and the refusal names a real way out, not a fictional one.** `_require_membership` gates every channel-management action including adding a NEW member, so a channel with zero human members would have nobody left in the tenant able to ever add themselves back in — the same class of problem `agent_count` solves for agents, but with no rescue path, since there's no way to see "0 human members" from outside and no way back in. **There is no delete-channel or dedicated leave endpoint in this codebase** (`channels.py` has exactly the 7 routes: create, list, get, add/remove user, add/remove agent — confirmed by reading the file, not assumed) — checked explicitly before writing the block, because a 409 telling someone to "delete the channel" when that action doesn't exist would be exactly the kind of dead-end refusal this build keeps having to go back and fix. The real, honest way out: `remove_user_member` only blocks when the target would be the channel's *only* human member — add a second person first (still allowed while alone, since you're still a member), then removing yourself succeeds because you're no longer the last one. Confirmed live end-to-end: leaving while alone shows "You're the only person in this channel — add someone else before leaving..." and the Members modal stays open; adding a colleague then clicking Leave succeeds, resets the chat view, and the channel drops out of your own sidebar (it still exists for the colleague).

  In practice this guard can only ever fire on self-removal: reaching the endpoint at all requires already being a member, so if exactly one member remains, it can only be the caller — no separate "removing someone else who happens to be the last one" case exists.

- **`@mention` autocomplete shipped 2026-09-05 (Wunomo Projects Phase 2 frontend, slice 8) — a pure frontend feature, no backend change.** `MessageThread.tsx`'s composer detects a leading, in-progress `@token` (regex `^@(\S*)$` against the live draft) and shows a dropdown of *that channel's own current agent members* — never every tenant agent, since suggesting one that isn't a member yet would offer a selection guaranteed to hit slice 6's own "isn't a member yet" error.   **A real bug found and fixed during this slice's own verification**: Escape dismissed by exact query-text match (`mentionDismissedFor === query`), so dismissing a bare `@` (empty-string query) permanently suppressed the dropdown on every future bare `@` typed into that same message — retyping it reproduces the identical empty query the dismissal was keyed on.
