00

The reset

You said you aren't convinced by the current direction. Having read the backend documentation, the user-flow doc, the build guide and the criticism report — I agree, and I can name exactly why. It isn't the backend. The backend is the strongest asset you have. It's the shape of the product sitting on top of it.

The one structural problem

The current frontend plan exposes the backend's organisation as the user's navigation. Sources, Pipelines, Runs, Quality, Incidents, Governance, Transformations, CI/CD — thirteen API segments became thirteen places a user has to visit and understand. That is a DataOps console. Your vision is a company that hires employees.

A business owner does not want to "configure a quality rule on source 3." They want to say: "@dataops the vendor file is dirty again, clean it and tell finance." Everything in the API surface should stay — it just stops being furniture the user walks around, and becomes a tool the employee picks up.

Updated 19 Sept — after reading the code

The critique above was written from your documentation. A read-only audit of the actual repository has since shown that the September frontend rebuild already moved to the project-centric paradigm this document argues for — projects, hired agents, per-project workbenches, and eleven old top-level screens deliberately retired into them. So the structural argument here is largely a description of a decision your team already made, not a correction to it.

What remains true is the part you can feel: the product still reads as a chatbot rather than a workforce. Section 16 now names exactly why, in three items, verified against code.

The design rule this whole document obeys

If a user has to leave the chat to do it, it's a design bug. Every other screen in Wunomo exists to watch work, approve work, or retrieve work — never to perform it. Performing happens in one place.

Five rules

#RuleWhat it changes
1Chat is the only verbUploading a CSV, connecting Postgres, hiring an employee, approving a payout, scheduling a recurring job — all done by talking. No "Add source" form anywhere in the product.
2The dashboard is a live x-ray, not an archiveCommand Center shows only what is moving right now. Idle employees, finished projects and stale metrics are not rendered. Zero-state is a feature, not a failure.
3Employees are hired into projects, not into the accountAn employee belongs to a project's team. The same personality can be hired twice with different names, memory and permissions — "Ravi (Finance)" for Ops and "Meera (Finance)" for Retail.
4Every consequential act passes a humanApproval isn't a separate module. It's a card in the chat, in-line, with the diff and the cost, blocking the run until you click. The Approvals inbox is just a second door to the same cards.
5Employees talk to each other in the openAgent-to-agent handoffs render as visible messages in the project thread — never as hidden background magic. If Finance asks HR for the shortlist, you see it happen and can interrupt.

What is preserved, unchanged

Nothing in the backend is thrown away. Everything gets re-labelled for a business user and re-routed through the chat. Full mapping is in section 16.

One honest caveat before you approve anything

The criticism report listed 12 critical issues. The code audit shows several are already resolved — role management, permissions and Google OAuth all exist and are tested. Four remain open and none are design problems: tenant isolation by convention rather than enforcement, a dev JWT signing secret set to a founder's name, a committed demo password, and an unverified Python execution sandbox. Section 16 has the corrected list. I've marked the places where the UI makes a promise the backend can't yet keep, so you don't ship a screen that lies.

Why "Project" is the container, not "Agent"

The build guide's structure was /workspace/agents/[id] — one chat per agent. That kills the single most valuable thing in your vision: cross-employee collaboration. If HR and Finance live in separate chats, they can't hand work to each other in front of you, and you become the courier between them — exactly the human middleman you're trying to remove.

Making Project the container gives you: one thread where the whole team is present, @-mention addressing, visible handoffs, a shared file context, and a single progress number that actually means something.

Density, radius, motion

RuleValue
Spacing4px base — 4 / 8 / 12 / 16 / 24 / 32 / 48 / 64. Chat messages sit on a 16px rhythm, dashboard cards on 12px gaps.
Radius6px inputs and badges · 8px buttons · 12px cards · 16px modals and drawers · 999px pills. Radius encodes elevation — bigger radius means further from the page.
Reading widthChat column capped at 720px. Employee output blocks can break out to 1040px for tables. Nothing runs edge to edge.
MotionOnly three animations exist in the product: (1) the working-pulse on an active employee avatar, (2) progress bars moving, (3) a new message sliding up 6px over 140ms. No card hover lifts, no page transitions, no gradient sweeps.
ElevationBackground difference only — no drop shadows except on drawers and modals. The console must stay flat so status colour is the only thing that pops.
IconsLucide, 16px in UI / 18px in nav, stroke 1.5, monochrome, inherit text colour. No icon ever sits in a coloured circle.

What deliberately has no tab

Pipelines, Runs, Quality rules, Incidents, Lineage, Transformations, CI/CD. Every one of these still exists in the backend and is fully used — but a business owner should never have to know the word "pipeline". They surface as:

  • Recurring work — a section on the employee's profile page and a line in the project's right-hand panel ("Ravi reconciles the ledger every Monday 07:00").
  • Trust score — quality rules become a 0–100 number stamped on every output, expandable into the checks that ran.
  • Raised hands — incidents become an employee message in chat, plus a red card on Command Center.
  • "How was this made?" — lineage + transformations + the SQL, behind one link on every output.
Power-user escape hatch

DataOps engineers are a real persona in your docs and they do want the raw console. Every one of the hidden surfaces is reachable at /w/advanced/*, linked only from Settings and from ⌘K. It ships, it just isn't in anyone's way. This is how you serve Persona A without letting Persona A's needs design the product for Persona C.

The chat command language

If chat is the only interface, chat needs a grammar. This is the complete surface — three prefixes and eleven commands. Everything else is plain English and gets routed by the orchestrator.

How a message is parsed

TokenMeaningBehaviour
@nameAddress an employeeCreates a task assigned to that employee. Multiple mentions → multiple parallel tasks from one message. Tagging someone not on the project offers to hire them inline.
@everyoneBroadcastEach employee decides whether the message is theirs. Used for context-setting: "@everyone we've moved the deadline to the 4th."
#nameReference a file or outputResolves against project files first, then workspace outputs. Autocompletes. Prevents re-uploading the same file.
/commandStructured actionThe eleven below. Everything else is conversation.
no prefixPlain instructionRouted to the most likely employee by capability match. If ambiguous, the system asks once: "Ravi or Meera?" — with buttons, not a typed answer.

Dependency detection — the thing that makes multi-agent work real

When one message contains "@Priya screen these… @Ravi once Priya has the shortlist, cost it out", the orchestrator must recognise that Ravi's task depends on Priya's output and must not start immediately. That's a LangGraph edge, and it's the single most important piece of backend work this design implies.

Trigger phrase familyResulting graph
"once / after / then / when X is done"Hard dependency. Task B stays queued until Task A emits an output. Shown in chat as "Ravi is waiting on Priya."
"and also / meanwhile / at the same time"Parallel. Both start immediately.
"give it to / hand it to / pass it to"Explicit handoff. A handoff card renders with the payload summary.
No temporal cueDefault to parallel, but if Task B's input schema can only come from Task A's output, infer the dependency and say so in chat rather than silently deciding.

Employee catalogue

Your documentation lists fifteen personalities. Exactly one is built. That's not a problem — it's a sequencing decision you need to make consciously, because the product promise on the landing page must match what a user actually finds behind the hire button.

The credibility trap

"Hire a full AI workforce" with one working role is the fastest way to lose an alpha user in the first session. Two honest options: (a) launch with 3–4 genuinely working roles and market the workforce, or (b) launch with DataOps + Analyst, market it as "your data team", and let the workforce framing arrive with the roster. This design supports both — the hire drawer already shows unbuilt roles dimmed with a quarter against them.

My recommendation on sequencing

  1. DataOps + Analyst — finish what exists. These two already cover your documented Persona A and B, and they're the pair that proves the multi-employee handoff without needing a single new connector.
  2. Finance Ops — the clearest money story ("it closed our books"), and it's mostly transformation and quality logic you already run.
  3. Founder Copilot — no new integrations, orchestrates the other three, and it's the role that makes the workforce metaphor click.
  4. HR Manager — first genuinely new tool surface. Only after the platform mechanics are proven, because it will expose every weakness in the handoff and permissions model.

Four working employees is enough to legitimately say "hire a team". Fifteen half-built ones is a demo that collapses under a real user.

Stage 1 & 2 — engineering spec

The two pieces of work that stand between the current system and this blueprint. Neither depends on the six open decisions in section 18, so both can start immediately. Stage 1 is a week. Stage 2 is the risk.

Stage 1 — streaming

Largest felt improvement per line of code, and it touches no data model. The existing graph already supports it; nothing calls the streaming interface.

ItemSpec
TransportServer-sent events, not WebSocket. One direction, works through every proxy, reconnects for free, and you don't need bidirectional yet. A new route alongside the existing one — POST /api/v1/chat/stream — leaving POST /api/v1/chat/ untouched so nothing currently working breaks.
Sourcerun_agent() currently calls .ainvoke(). Add a sibling that calls .astream_events(version="v2") on the same compiled graph. The graph, the tools, the approval gate and the caching all stay as they are.
Event schemaSix types, and no more: token (text delta), tool_start (name + args summary), tool_end (result summary), approval_required (the approval row id), error, done (final message id + usage). The frontend renders each differently — this is what makes tool calls visible as they happen rather than as a trace after the fact.
PersistenceUnchanged. Accumulate the same way the buffered path does and write the same ChatMessage rows at the end. A dropped connection must still persist what completed — write on stream close, not only on clean finish.
Quota and budgetenforce_quota("ai_credits") and enforce_agent_budget() run before the stream opens, as now. A 402 is a normal HTTP error, not an SSE event.
Frontendlib/api.ts gains one streaming function. components/chat/MessageThread and ToolCallBlock already model tool calls — they render incrementally instead of once.

Stage 2 — the supervisor and the handoff

One message, several employees, a dependency between them, and a visible pass of work. This is the thing that makes Wunomo a workforce, and the audit confirms no code path does it today.

The graph

NodeResponsibility
parseTakes the raw message. Resolves every @mention against channel membership — mentions.py already does this. Emits one intent per mentioned agent, each with the slice of the message addressed to it.
planDecides ordering. Produces a DAG of task intents with explicit edges. Uses the phrase families in section 14 plus an input-schema check: if B's required input can only come from A's output, infer the edge. When it infers an edge the user didn't state, it must say so in the thread — never silently reorder.
dispatchCreates one Task row per intent, reusing the existing tasks/task_steps lifecycle rather than inventing a parallel one. Tasks with no unmet dependency go to queued; the rest wait.
runInvokes the existing per-agent graph, unchanged, once per ready task. Parallel where the DAG allows. This is the node that reuses everything already built.
handoffOn completion, writes a Handoff row, posts the handoff card to the thread, and releases dependents.

The one new table

ColumnNotes
id, tenant_idReal FK to tenants.id — don't inherit the bare-tenant_id convention for a new table.
channel_id, project_idWhere it happened. FK both.
from_agent_id, to_agent_idFK to agent_instances.id.
from_task_id, to_task_idFK to tasks.id. This is the dependency edge, persisted.

payload_refPointer to the actual artefact. Not the artefact itself.
withheldJSON. What was deliberately not passed — the "Ravi did not receive names or contact details" line. This is a privacy feature, not decoration.
created_atNaive UTC, matching the codebase convention outside cicd.py.

Failure semantics — decide these before writing code

SituationBehaviour
Task A fails, B depends on itB moves to blocked, not failed. The thread says which upstream task broke. Retrying A releases B.
Task A needs approvalA holds, B holds behind it, and the approval card names both — "approving this also unblocks Ravi's costing." Users must see the full consequence of one click.
User sends a new message mid-runRunning tasks continue. The new message is parsed against current state. If it contradicts a running task, ask rather than guess.
Circular dependency inferredRefuse to dispatch, say so plainly, and ask the user to order it. Never deadlock silently.
Agent mentioned but not on the projectOffer to hire inline (section 07.2). Don't fail the whole message.
Step budget exhausted mid-DAGExisting step_budget_max applies per task. The DAG needs its own ceiling too, or one ambiguous message can fan out expensively.

The acceptance test

Headless, no UI, written before the implementation. This single test is the gate between stage 2 and everything downstream.

  • Given a channel with two agents of different employee_type.
  • Post one message: "@a summarise this file, then @b count the rows in a's summary."
  • Assert: two Task rows, B queued behind A rather than started, exactly one Handoff row linking them, B's input containing A's output, and both reaching done in the right order.
  • Then repeat with A forced to fail, and assert B lands in blocked with the upstream task named.
If stage 2 turns out to be hard

That's a finding, not a setback — and you want it in week two. The fallback is honest and still valuable: sequential handoffs only, no parallelism, user-confirmed ordering rather than inferred. Less magical, entirely shippable, and it still beats every product where the agents can't talk to each other. Decide the fallback now so you're not making that call under deadline pressure.
