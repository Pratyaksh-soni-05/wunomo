## 1. Architecture Summary

**Stack:** FastAPI (async, Python 3.11/3.13) + SQLAlchemy 2.0 async + PostgreSQL 16 + Redis + Celery (worker + beat) + LangGraph/LangChain v1.x agent (`gemini-3.5-flash` primary, Llama 3.3 70B via Groq fallback) + Next.js 15/React 19 frontend (source present but incomplete — see §2).

**Services** (`dataops-agent/docker-compose.yml` and `backend/docker-compose.yml` — two near-duplicate compose files exist, see Gotchas):
- `backend` — FastAPI app (`backend/main.py`), port 8000, mounted as a live volume (`./backend:/app`) so container edits are picked up without rebuild.
- `postgres` — Postgres 16-alpine, port 5432, db `dataops`.
- `redis` — Redis 7-alpine, port 6379. DB 0 = general cache, DB 1 = Celery broker, DB 2 = Celery result backend (`config.py`).
- `celery_worker` / `celery-worker` — runs `celery -A services.celery_app worker --concurrency=4`.
- `celery_beat` / `celery-beat` — runs the periodic scheduler (static + dynamically-registered per-pipeline schedules).
- `frontend` — **commented out** in root `docker-compose.yml`. Not started by `docker compose up` even if the source existed and built.

**Core end-to-end flow (chat → agent → tool → approval):**
1. Client calls `POST /api/v1/chat/` (JWT-authed) or connects to `WS /ws/chat/{tenant_id}/{session_id}` (⚠️ **unauthenticated**, see §2/§3).
2. `agent/dataops_agent.py` runs a LangGraph `StateGraph`: `inject_system` → `agent` (LLM bound to all tools via `.bind_tools`) → `approval_gate` → conditionally `tools` (a stock `ToolNode`) → loops back to `agent`, or `END`. Hard cap of 20 iterations, no config knob.
3. `personality.py` supplies the system prompt per `PersonalityMode` (engineer/founder/analyst/auditor) and gates tool calls per `OperationMode` (advisory/assisted/autonomous/audit) via `requires_approval()`, which checks a hardcoded `RISK_ACTIONS` risk table (low/medium/high).
4. If a tool call requires approval, `approval_gate_node` blocks it and injects an "Approval Required" message into the chat — but (see Gotchas) this in-graph gate is **not the same system** as the DB-backed approval queue read by `GET/POST /api/v1/approvals`.
5. The real, DB-backed approval workflow lives in `modules/governance/policy_engine.py` (`PolicyEngine`): a request is created, an admin/owner calls `POST /approvals/{id}/approve`, which calls `execute_approved_action()` → looks up the action in a hardcoded `TOOL_REGISTRY` dict → dynamically imports and invokes the real function via `importlib`.
6. Tool implementations live in `agent/tools/*.py`, one file per domain (ingestion, transformation, quality, orchestration, observability, governance, reporting, cicd), and call into `modules/*` for the actual work.

**Data model & tenancy:** Postgres, 17 SQLAlchemy models across `models/all_models.py` (13 models: Tenant, User, DataSource, Pipeline, PipelineRun, QualityRule, Incident, LineageNode, LineageEdge, AuditLog, ApprovalRequest, ChatMessage, DataContract, UsageMetric, KpiValue) and `models/cicd.py` (3 models: PipelineCommit, PipelineDeployment, CICDIncident). This is **multi-tenant by convention, not by enforcement**:
- Every model except `Tenant` carries a `tenant_id` column, but only `User`, `DataSource`, and `Pipeline` make it a real FK to `tenants.id` — the other 13 use a bare `String` with no FK constraint.
- Tenant scoping is entirely manual: `get_current_user()` decodes the JWT and returns `tenant_id` straight from client-supplied claims (no DB re-check); every endpoint/manager class is individually responsible for adding `.where(Model.tenant_id == tenant_id)`. There is no base query class, no session-level hook, no middleware, and **no Postgres RLS** (`create_enums.sql` only defines enum types).
- Spot-checked call paths (`dag_manager.py`, `policy_engine.py`, `run_tracker.py`, `rule_engine.py`, `connector_manager.py`, `schema_profiler.py`, `sql_runner.py`, all of `api/v1/`) do filter correctly today. The invariant holds only as long as every future query remembers to add the filter — nothing in the framework enforces it. Treat "did you scope this query by tenant_id?" as a mandatory review question for every new query in this codebase.

**Background jobs (Celery):** static beat schedule in `services/celery_app.py` — freshness check every 15 min (real), anomaly detection hourly (stub, logs only), daily reports every 24h (stub, logs only), CI/CD post-deploy health check every 60s (real). `modules/orchestration/scheduler.py` additionally injects **dynamic per-pipeline schedules** into `celery_app.conf.beat_schedule` at runtime, parsed from each pipeline's `schedule_cron` via a hand-rolled cron parser (not `croniter`, despite `croniter` being a dependency) — `Scheduler.register()`/`sync_all()` compared pipeline status against `PipelineStatus.active` (lowercase, doesn't exist — real member: `.ACTIVE`) until fixed and live-verified this session; every active-pipeline filter here silently matched nothing before that. Pipeline "DAG" execution (`modules/orchestration/dag_manager.py`) is **not actually a DAG** — no step graph, no topological sort; a "run" is a fixed linear sequence (sync source → run quality checks → mark result).

## 3. Known Gotchas

*This section only grows. Append; never delete. If a gotcha turns out to be fixed, mark it `[RESOLVED: <how/when>]` rather than removing it.*

- **Two docker-compose.yml files, not one.** `dataops-agent/docker-compose.yml` (root, referenced by the README quick-start) and `dataops-agent/backend/docker-compose.yml` both stand up the full stack independently, with different container/network names and different Postgres/Redis healthcheck behavior. Running both simultaneously will port-collide on 8000/5432/6379. Always confirm which one a command/doc is referring to before running `docker compose` commands.
- **The frontend service is commented out in the root compose file.** `docker compose up` never starts a frontend even after the missing files are restored — you must uncomment it in `dataops-agent/docker-compose.yml` first.
- **`.gitignore` in this repo only covers Python.** `[RESOLVED: initial commit]` — a Node/Next.js block (`node_modules/`, `.next/`, `out/`, `.vercel`, `.turbo/`, etc.) was added before the first commit, and the ~11.5k already-staged `node_modules`/`.next` files were unstaged. Still double-check `git status` after any broad `git add -A`/`git add .` inside `dataops-agent/frontend/` in case new build output reappears.
- **JWT tenant_id is trusted, never re-validated against the DB — and this applies to every claim in the token, not just tenant_id, including `role`.** `get_current_user()` (`api/v1/auth.py`) is a bare `jwt.decode()` with no DB lookup at all — no `is_active` check, no fresh `role` read, nothing. If you ever add a "deactivate tenant," "remove user from tenant," or "change a user's role" feature, remember that a previously-issued JWT for that user stays valid, **with its original claims**, until it naturally expires — there's no revocation and no per-request re-check. Concretely: `PATCH /team/members/{id}/role` updates the DB row, but the affected user's *existing* session keeps operating under their *old* role (both for `require_role()` gates and for whatever the frontend decodes client-side via `decodeUserFromToken()`) until they get a fresh token — either by naturally re-logging-in, or by the token expiring and them being forced to. Same for `DELETE /team/members/{id}`'s soft-removal (`is_active = False`): the removed member's still-valid JWT continues to be accepted by every authed endpoint, unchanged, until expiry — **confirmed live during Phase 17's Team build** (a JWT captured immediately before removal was replayed against `GET /team/members` afterward and returned a real `200`). The only path that's actually real-time is a *fresh* login attempt, since `resolve_password_login()` filters `is_active` at that specific moment (see the separate, already-documented Gotcha that this still isn't true for Google/email-code login). **When building any UI around role/removal, don't imply the effect is immediate for an already-open session** — it's immediate for the DB and for anyone who logs in fresh afterward, not for a session already in flight. **This is now tracked as a real fix item, not just documented behavior — see the new "Removed/demoted members keep access for up to the JWT TTL" Known-broken row below** (severity, exact TTL, and fix directions).
- **Tenant scoping is a per-query convention, not a framework guarantee.** Every new query against a tenant-owned table must manually add `.where(Model.tenant_id == tenant_id)`. There is no base repository/query class to inherit this from. When reviewing or writing any new DB query in this codebase, explicitly check for the tenant filter — it is the single easiest way to introduce a cross-tenant data leak here.
- **Two different LLM fallback mechanisms coexist.** `services/llm_service.py` has both `get_llm_for_agent()` (LangChain `.with_fallbacks()`, used by the actual agent graph) and `invoke_llm()` (manual tenacity-retry + manual fallback, apparently unused by the graph). Don't assume changing one changes the other's behavior.
- **Ingestion connectors expose a raw `execute_sql()` that bypasses `SqlRunner`'s safety layer.** `SqlRunner` (the safe, keyword-blocked, parameterized path) is one specific caller; `postgres_connector.py` and `mysql_connector.py` both independently expose `execute_sql()` methods that run arbitrary SQL with no keyword filtering. If you add a new caller, go through `SqlRunner`, not the connector directly, unless you've deliberately re-derived the same protections.
- **`python_runner.py`'s in-process `exec()` sandbox is intentionally not airtight.** It AST-allowlists imports/names and uses a restricted builtins namespace + thread timeout, but the code's own docstring says this is "sufficient" only for already-LLM-validated code, not untrusted input, and recommends a real microVM (gVisor/Firecracker) for anything stronger. Don't expose this path to raw user-submitted Python without adding real process isolation first.
- **Debug/patch scripts in `backend/` root are leftover hotfixes, not part of the app.** `diagnose.py`, `fix_analytics.py`, `fix_analytics2.py`, `patch_analytics.py` were run manually inside the container (they hardcode the `/app/...` container path) to patch a `NoneType has no attribute 'value'` crash in `/api/v1/analytics/pipelines` caused by NULL pipeline-status rows in a groupby. The underlying fix should already be reflected in `api/v1/analytics.py` itself — if you're debugging analytics and considering writing a new one-off patch script, first check whether `analytics.py` already has the fix these scripts describe, and prefer fixing it in place over adding another patch script to the pile.
- **Test suite hits whatever DB `APP_ENV=test` resolves to — there's no isolated test DB or per-test reset — and the same is now true of Redis for anything rate-limited.** `conftest.py` builds an `AsyncClient` against the real `main.app` with no fixture-level DB setup/teardown. Running tests repeatedly can accumulate rows; use a unique/random email per test (most tests already do — `test_register_and_login` didn't, and a hardcoded email accumulating duplicate tenants across repeated runs is exactly what made login()'s disambiguation fix start (correctly) failing that test — fixed by giving it a unique email like everything else). The email-code auth system's Redis-backed rate limiters (`services/auth_service.py`) have the identical problem in a new form: the per-IP counter (`otp:ip:{ip}`) is shared across every test run in a session, real curl testing, and the pytest ASGI test client alike, since none of them get a distinct IP and Redis state isn't reset between invocations. Heavy manual live-testing against `/auth/email-code/request` right before running `pytest` can leave the per-IP counter primed near/over its cap, causing an unrelated later test run to fail with `rate_limited` for reasons that have nothing to do with that run's own test logic. If an email-code test fails this way, check `redis-cli KEYS "otp:*"` before assuming the code is broken — `redis-cli --scan --pattern "otp:*" | xargs redis-cli DEL` clears it (safe, it's all short-TTL test/dev state). Don't assume test runs are hermetic, for either store.
- **`RISK_ACTIONS["high"]` names tools that don't exist** (`delete_records`, `drop_table`, `modify_schema`, `revoke_access`). If you're asked to "make destructive actions require approval," check whether the actual mutating tool (e.g. `execute_sql_transform`, `resolve_incident`) is even in that risk table before assuming the gate already covers it — right now, most real mutating tools default to whatever risk tier `get_risk_level()` falls back to, not `"high"`.
- **Approvals created mid-chat (via the LangGraph `approval_gate_node`) do not show up in the `/api/v1/approvals` queue.** Only approvals created through `PolicyEngine.create_request()` (e.g. via `seed_approval.py` or a correctly-written tool) persist to the DB. If a user reports "the agent said it needs approval but I don't see it in the approvals list," this is why — check whether the code path that created it actually called `create_request()`.
- **Celery beat's scheduled pipeline-run task call looks arg-mismatched** (see Status Table). Don't assume scheduled pipelines are exercising the same code path as manually-triggered ones until this is confirmed/fixed.
- **`RunTracker` is a pass-through, not a separate system.** It exists only "for agent tool compatibility" (per its own comment) and just delegates to `DAGManager`. Don't look for run-tracking logic there — it's in `dag_manager.py`.
- **There is no real DAG.** Despite the name `DAGManager` and the module path `modules/orchestration/`, pipeline execution is a fixed linear sequence (sync → quality check → done), not a graph with dependency resolution. If a task asks you to add a new pipeline step, you're inserting into a linear chain in `tasks.py`'s `_execute_run`, not registering a DAG node.
- **Any LangGraph node you add to `agent/dataops_agent.py`'s `StateGraph` must return only the new/delta value for reducer-annotated channels, never the full accumulated state.** `AgentState.messages` uses `Annotated[Sequence[BaseMessage], operator.add]`, so LangGraph automatically appends whatever a node returns onto the existing value. Returning `state["messages"] + [new]` (instead of just `[new]`) — which every custom node in this file did until the fix — makes the reducer concatenate old+new onto the already-accumulated state, doubling history on every node hop (a 3-message conversation reached 63 messages in 3 turns). `ToolNode` (the one prebuilt node here) has always done this correctly; match its pattern for any new custom node.
- **Any new tool exposed to the agent must never accept `tenant_id` (or `user_id`/`session_id`) as an LLM-suppliable argument that isn't also force-corrected server-side.** Tool schemas require these as function-call arguments the LLM itself generates, but the LLM has no reliable way to know the real value — it will hallucinate a placeholder unless told, and can still get it wrong even when told. `agent_node` in `dataops_agent.py` now force-overwrites `tenant_id` on every outgoing tool call to the real, server-derived value; if you add a tool that takes `tenant_id` (or add `user_id`/`session_id` as tool args for the first time), extend that same override loop rather than trusting the LLM's argument. All tools in `ALL_TOOLS` now take `tenant_id` this way — `get_cicd_status` was the last holdout and is fixed (see Status Table).
- **`FALLBACK_LLM_MODEL` must be a model capable of reliable tool-calling.** `llama-3.1-8b-instant` on Groq fails real tool-calling requests outright with a `tool_use_failed` 400 error (malformed function-call generation) — it only ever looked "fine" in testing that didn't exercise tool calls. Keep this set to `llama-3.3-70b-versatile` (or an equally capable model) — `config.py`'s own default already documents this; don't let `.env` drift back to a cheaper/faster model without re-testing an actual tool-invoking chat message live.
- **No agent tool should ever call back into this app's own REST API over HTTP.** Tools should call the same service-layer functions the REST endpoints call, in-process — that's the pattern every tool follows (`modules/*` classes, or plain functions in `services/*.py` like `cicd_service.py`). An HTTP round-trip back into your own API (`get_cicd_status` did this until fixed — see Archive) is a sign a tool was stubbed out before the shared service layer existed, and it silently loses auth/tenant context in the process: `httpx` doesn't raise on a 4xx by default, so a failed/unauthenticated self-call can return empty defaults (`{}`, `0`, `"unknown"`) instead of an error. Treat any tool whose failure mode is unusually generic zero/empty defaults as a signal to check whether it's swallowing a failed call this way.
- **"Verified live" only proves the exact code path that specific test exercised — write regression tests against the real model/schema, not assumptions about column names.** `get_pipeline_for_repo()` referenced `Pipeline.is_active`/`Pipeline.source_config`, neither of which exist (real columns: `status`, `pipeline_config`) — it would have raised `AttributeError` on its very first real call, forever, since the function was written. There was no mock or fixture to blame (no automated test existed for it at all); the original fix was verified manually/live, and that manual pass most likely exercised a different code path (setting `pipeline_config` at pipeline-creation time, which has always used the correct field name) than the one that was actually broken (the function itself, plus the update path). When you add a regression test for a DB-touching fix, prefer hitting the real model via a real session (see `test_cicd_service.py`, `test_pipeline_run_status.py`) over a hand-rolled mock — a mock can only be wrong about the schema in the same way the code under test is already wrong, silently agreeing with itself.

Found while writing a regression test for the dict-arg-stringification bug above: a fake tool with a `config: dict` parameter failed with `TypeError: missing 1 required positional argument: 'config'` even though the value was correctly present and correctly typed right up until the actual function call — renaming the test's parameter to `payload` fixed it immediately, isolating the cause. **`orchestration_tools.py`'s real `create_pipeline(tenant_id, name, source_id, config: dict)` has this exact collision** — its `config` argument has never once reached `DAGManager.create_pipeline()` correctly, independent of anything else wrong with that call site; renamed to `pipeline_config` (matching the real `DAGManager` method's own parameter name) as part of the 22-site tool punch-list fix. **Never name a `@tool`-decorated function's parameter `config`** — pick anything else (`pipeline_config`, `settings`, `options`, etc.).
- **Groq's daily TPD (tokens-per-day) quota is a rolling window, not a fixed daily reset — a successful cheap probe after a 429 does NOT mean the quota is meaningfully free again, and a bigger request right after can re-exhaust it instantly.** Found live in the Phase 10 session: after a `429` reporting "try again in ~14m," a tiny no-tool probe (`"Say OK."`) succeeded a few minutes later — read as "the quota freed up." It hadn't, in any durable sense: the very next request (a real tool-calling chat message, much larger token cost from the full system prompt + tool schemas) immediately 429'd again, this time reporting `Used 99968/100000` and **"try again in 1h5m."** The window is sliding/rolling (old usage ages out continuously, freeing a few tokens at a time), not a hard reset at a fixed daily boundary — a small cheap request can slip through a brief trickle while the budget for anything larger is still effectively zero. **Don't treat one successful cheap request as proof the quota is usable again** — if the next real request 429s with a large "try again" figure, the trickle is gone and the wait is real; budget for the worst case (the large figure), not the optimistic one (the probe that happened to succeed). Also confirms Groq's TPD budget is shared at the **organization** level (`org_01km8sb853e2tvhp21df5zga6f` in every error seen across every session so far) — every tenant/test/session in this project draws from the same pool, so cumulative usage across unrelated work compounds within a day.
- **A long `sleep` backgrounded with `run_in_background: true` (or a manually-`disown`ed shell sleep) is not reliable for waits longer than a couple minutes in this environment — it can report "completed" almost immediately with an empty log, without the sleep actually running to completion.** Found live waiting out a Groq quota cooldown: a `(sleep 720 && node combined-verify.js) &` backgrounded command reported `completed, exit 0` after roughly 2 real minutes, with a 0-byte log — the sleep never ran to term. Switched to a `until <curl probe succeeds>; do sleep 30; done` polling loop (also `run_in_background: true`, no manual `disown`) instead, which behaved correctly and fired one clean notification when the real condition (a successful chat response) was met. **For any real external-system wait in this project (LLM quota resets, webhook delays, etc.), prefer a polling `until`-loop over a bare long `sleep`**, even when backgrounded — a bare sleep's completion signal cannot be trusted to mean the duration actually elapsed.
- **`User.is_active` is only enforced on the password login path (`resolve_password_login()`, fixed in Phase 15) — Google login and email-code login (`resolve_identity()`) still don't check it at all.** A deactivated/removed team member can still log in via Google or email-code even after Phase 15's `DELETE /team/members/{id}` sets `is_active=False`, since `resolve_identity()`'s queries have no `is_active` filter (deliberately out of scope for the pass that fixed the password path — fixing all three consistently is its own small piece of work). **Before trusting "member removal actually blocks login" for anything beyond the password method, add the same `is_active` filter to `resolve_identity()`.** Also note this doesn't touch any JWT already issued before removal — that's the separate, already-documented "no JWT revocation" gap below.
- **A file with no trailing newline can cause `Read` to silently omit its last line from view, and an `Edit` insertion right at that boundary can then orphan that line into whatever gets inserted after it.** Found live while adding `TeamInvite` to `models/all_models.py` (Phase 15): `all_models.py` had no trailing newline, so a `Read` of the tail of `TransformRun`'s class body didn't show its actual final field (`created_at`) — an `Edit` appending the new `TeamInvite` class right after what looked like the last line inserted it *before* that real final line instead, orphaning `TransformRun.created_at` (dropped it entirely, causing real `AttributeError`s at query time — `test_transform_runs_list.py` went from passing to 5 failures) and silently duplicating a stray second `created_at` inside `TeamInvite`. Root-caused via `git diff`, not guesswork — the diff made the exact misplacement obvious immediately. **When appending a new class/section at the end of a model (or any) file, confirm the insertion landed where intended with `git diff` right after the edit** — don't just trust that the tool call succeeded, especially for files that might lack a trailing newline (Python files at the end of an editing session are a common case).
- **Running `docker compose restart backend` (or any DB-mutating `docker exec`) while a `docker exec dataops_backend python -m pytest` is still executing in the background corrupts that test run — spurious failures and a wildly inflated reported duration, not a real regression.** Found live during Phase 15: backgrounded a full-suite run, then (not knowing it was still in flight) restarted the backend container and ran several manual `docker exec` DB-mutation scripts for live RBAC verification. The backgrounded pytest eventually reported `1 failed, 132 passed in 12034.25s` (**3.3 hours**, vs. the normal ~118s) — `test_catalog.py::test_catalog_source_id_filter` failing with `KeyError: 'count'`. Re-running that single test in isolation immediately after: 5/5 passed in 12s. Re-running the full suite in isolation: 133 passed in 117.81s — completely clean. The concurrent restart/DB-mutation activity was corrupting the exec'd pytest process's DB state/connections mid-run, not exposing a real bug. **Never run `docker compose restart <service>` or other DB-mutating commands against a container while a test suite is still running inside it in the background** — either wait for the backgrounded suite to finish first, or don't background it if you know you'll need the container for something else in the meantime.
- **This project's Resend account is still in sandbox mode — `onboarding@resend.dev` can only deliver to the account owner's own verified address (`pratyakshsoni2005@gmail.com`), not arbitrary recipients.** Confirmed live at the start of Phase 15: a real send to `ps6664@srmist.edu.in` (a different real address) got a real `403` directly from Resend's API — `"You can only send testing emails to your own email address (pratyakshsoni2005@gmail.com). To send emails to other recipients, please verify a domain at resend.com/domains..."` — and the identical call against the owner's own address succeeded with `last_event: "delivered"`. This is invisible from inside the app: `_send_code_email()` (`services/auth_service.py`) deliberately never surfaces delivery failures to the caller (enumeration-safety by design, see Phase 3's rate-limiting design) — the request endpoint always returns `{"status":"sent"}` regardless, so a 403 only shows up in `docker compose logs backend` (`email_code_send_failed`), never in the API response. **Any invite-flow or email-code testing against a real third-party address (not the account owner's own) will silently fail delivery while the app reports success** — until a domain is verified at resend.com/domains and `EMAIL_FROM` switches off `onboarding@resend.dev`, real live-verification of email delivery is only possible against `pratyakshsoni2005@gmail.com` itself. Check `docker compose logs backend | grep resend` after any "was this actually delivered?" question, don't trust the API's `{"status":"sent"}` alone.
- **A React hydration-mismatch console warning fires on every page, app-wide, whenever `localStorage`'s theme is `"dark"` and the page does a full reload — a characteristic of the root layout's theme pre-paint script, not a per-page bug.** Found live during Phase 18's AI Employees build, only because that session's verification standard explicitly checked for zero console errors (including after a dark-mode reload) — no prior phase's verification appears to have checked this specifically. Root cause: `app/layout.tsx`'s inline pre-paint script sets `document.documentElement.dataset.theme = 'dark'` synchronously before React hydrates (the whole point — avoids a flash of the wrong theme), but the server-rendered HTML has no `data-theme` attribute at all, so React's hydration diff sees a real client/server mismatch on the `<html>` tag and logs the warning React itself describes as "won't be patched up." **Confirmed app-wide, not AI-Employees-specific**: reproduced identically on `/dashboard` and `/sources`, both long-shipped, previously-verified pages — this has presumably been happening since Phase 7 introduced the theme system, just never caught by a verification pass that checked console output this strictly. Cosmetic only (the page still renders correctly post-hydration; nothing visibly breaks), but it is a real, reproducible defect, not nothing. **Not fixed as of Phase 18** — a real fix would mean touching the root layout's pre-paint mechanism, which is cross-cutting (affects every single page, not isolated to whatever page happens to surface it), so per this project's own "fix now only if small/isolated" rule it wasn't fixed reactively inside an unrelated page's build. If a future session touches theme/hydration logic, or if Phase 19's Polish pass gets to console-error cleanliness, this is the entry to close — likely fix shapes: suppress hydration warning specifically on the `<html>` element (`suppressHydrationWarning`, a real Next.js-supported escape hatch for exactly this documented pattern), or restructure the pre-paint script to avoid a genuine attribute mismatch in the first place.

## 4. Workflow Rules

These govern how any Claude Code session (including this one) operates on this repo:

1. **Read this file in full at the start of every session before taking any action.**
2. **Work one issue or feature per session.** Verify each fix against the real running system (start the stack, hit the actual endpoint/flow, don't just eyeball the diff) before moving to the next one. Don't batch multiple unverified changes together.
3. **If verifying a fix surfaces a new or hidden related bug, resolve it in the same session** rather than stopping at the original scope — but still commit it separately (see rule 5).
4. **For any non-trivial feature or architectural change, propose the approach and tradeoffs first and wait for approval before writing code.** This includes anything touching tenant isolation, auth, the approval workflow, or the Celery scheduling mismatch — these are exactly the areas where a quick fix can silently reintroduce one of the gotchas above.
5. **Write or update a regression test alongside every bug fix, in the same commit.** Given current test coverage (auth + smoke only), most fixes in `agent/`, `modules/`, or `services/` will be the first test for that code path — that's expected, not a sign you're doing extra work.
6. **Commit after every individually verified fix**, with a message describing the issue and how it was verified. Don't batch multiple fixes into one commit.
7. **Update this file's Status Table and Known Gotchas section as part of the same commit** whenever something is fixed, added, or newly discovered. Move superseded information into the Archive below rather than deleting it.
8. Given there are no commits yet in this repo, the first commit is an unusually large diff — that's expected, but subsequent commits should follow the one-fix-per-commit rule above.
9. **When a fix supersedes an existing Known-broken row, mark that row `[RESOLVED: <how/when>]` in the *same* commit as the fix — never just add a new row and leave the old one riding.** This has already failed silently three times in this project (the `login()`/`register()` disambiguation rows, and `request_approval`, all fixed sessions before anyone marked them resolved) — each time because the fix's own commit only touched the Status Table, not the matching Known-broken row, and nothing ever prompted a later pass to reconcile them. A stale "known-broken" row is worse than no row at all: it actively tells a future session (or an outside reader, like the Phase 19 user manual) that something is still wrong when it isn't. Before closing out any commit that fixes a documented bug, grep the Known-broken table for that bug's description and update it in the same commit — don't defer it to a later cleanup pass.
